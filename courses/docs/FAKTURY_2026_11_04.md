## Chování

- Doklad vzniká po označení objednávky jako zaplacené v existujícím platebním workflow, nikoli pouhým otevřením náhledu. Nejde o zálohovou výzvu. Každý vystavený doklad uvádí „Neplaťte, již uhrazeno“ a zbývá k úhradě 0 Kč.
- Dodavatel, účet, IBAN, SWIFT, kontakty, konstantní symbol 0308 a sazba DPH 21 % vycházejí ze vzoru. Ceny objednávky jsou konečné včetně DPH. Základ a DPH se počítají desetinnou aritmetikou a zaokrouhlují na haléře za položku. Forma úhrady je „Platební brána“, neboť nebyla určena konkrétní metoda uvnitř brány.
- Odběratel se kopíruje výhradně z fakturačních polí Order. Kontaktní osoba slouží jako adresát potvrzení, není zdrojem fakturační adresy.
- Nové objednávky ukládají serverem vypočtené položky už při objednání. Současný checkout nabízí jeden kurz pro skupinu; renderer a snapshot podporují více položek, checkout tím nebyl rozšířen. U starších objednávek se použije uložená celková cena dělená počtem účastníků, nikdy aktuální ceník. Nejednoznačná cena nebo rozpor součtu vystavení zastaví.
- Číslo YYNNNNN se přidělí podle skutečného dne vystavení v Europe/Prague. Každý rok začíná 00001, limit je 99999 za rok. OneToOne vazba na objednávku, unikátní číslo i dvojice období/pořadí jsou vynuceny databází. První zápis v transakci získá zámek i na SQLite. PDF ani transport neběží pod tímto zámkem.
- Faktura ukládá kopii odběratele, dodavatele, loga, položek, daňového rozpisu a objednávkových dat. Datum splatnosti je datum vystavení jako ve vzoru. Datum uskutečnění plnění se zobrazuje podle uloženého data přijetí platby. Úspěšně vytvořené PDF se ukládá v databázi a další stažení vrací stejné bajty.
- Po selhání PDF zůstává již přidělené číslo. Další pokus znovu použije stejný doklad. Platební potvrzení se odešle až s připravenou přílohou; aktivace účastníků běží nezávisle. Po selhání transportu lze znovu spustit dosavadní workflow. Dřívější dokončené platební e-maily se automaticky znovu neposílají, ani když pocházejí z doby bez faktur.
- Staré zaplacené objednávky se migrací automaticky nefakturují. Doklad jim může vzniknout při výslovném opakování platebního workflow, s aktuálním datem vystavení.

## Náhled a přístup

- Stránka simulované brány /platba/<id>/ má nyní odpočet 30 místo 5 sekund a odkaz na samostatný náhled. Před platbou je náhled výrazně označen jako neúčetní a nemá číslo. Nečerpá číselnou řadu. Po potvrzení platby je dostupné skutečné PDF na potvrzovací stránce.
- Odkazy se zobrazují pro objednávky založené v aktuální relaci prohlížeče. Změna ID na cizí objednávku vrací 404. Samotná návštěva původních veřejných simulačních URL oprávnění k faktuře neuděluje. Relace uchovává posledních 50 vlastních objednávek; po jejím zániku řeší přístup oprávněný správce. Nezavádí se veřejné přihlášení přes číslo faktury ani automatický přístup zaměstnanců objednatele.
- Administrace má samostatný seznam Faktury. Staff potřebuje výslovné oprávnění courses.view_invoice, které přiděluje superuser. Samotné staff nebo oprávnění k objednávkám nestačí pro PDF. Faktury nelze v administraci měnit, přidávat ani mazat.
- Faktury se nevystavují do veřejného MEDIA adresáře. PDF i HTML náhled mají zákaz cachování prohlížečem.
- Stávající veřejná simulace platby je nadále pouze vývojový mechanismus, nebyla nahrazena platební bránou. Ostrá brána musí později volat workflow až po ověřeném potvrzení poskytovatele. Tato dodávka nenapojuje žádné skutečné platby.

## Lokální použití – PowerShell

1. Ověřte vlastní git status a zálohujte databázi. Rozbalte ZIP do kořene projektu; zachovejte adresářovou strukturu a nahraďte soubory. Balíček neobsahuje databázi ani .env.
2. Aktivujte stávající virtuální prostředí a ponechte e-maily v náhledovém režimu:

```powershell
$env:EMAIL_TRANSPORT = "preview"
python manage.py migrate
python manage.py check
python manage.py makemigrations --check --dry-run
python manage.py test courses
node --test courses/tests/cookies_frontend.test.cjs
python manage.py runserver
```

Použijte stávající DJANGO_SECRET_KEY z vlastního .env. Nové závislosti nejsou přidány; Chromium se používá stejně jako u certifikátů. Jestliže v konkrétním prostředí chybí, nainstalujte jej pod stejným účtem a ve stejném venv příkazem `python -m playwright install chromium`.

3. Vytvořte novou skupinovou objednávku. Na simulaci ověřte 30 sekund a odkaz na náhled bez čísla. Náhled se otevírá do nové karty, původní odpočet běží dál. Po návratu ověřte PDF, odběratele, počet účastníků, celkovou cenu a „Neplaťte“.
4. Přihlaste se jako superuser, zkontrolujte Faktury a případně přidělte konkrétnímu správci pouze právo zobrazování faktur. V anonymním okně ověřte odmítnutí stejné PDF URL.
5. Opakované stažení musí mít stejné číslo. Chcete-li opakovat nedokončené e-mailové workflow, použijte existující akci „Označit vybrané objednávky jako zaplacené“ i pro již zaplacenou objednávku. Stav zaplacení ani číslo faktury se tím neobnovují. Ponechte EMAIL_TRANSPORT=preview.

## Pozdější nasazení na PythonAnywhere

Commit, push ani nasazení nebyly provedeny. Až po jejich samostatném odsouhlasení:

- Před aktualizací zálohujte db.sqlite3 (nově obsahuje také uložená PDF) a zachovejte produkční konfiguraci.
- Pro současný testovací provoz ponechte EMAIL_TRANSPORT=preview. Tato změna sama nenastavuje SMTP ani platební bránu.
- Použijte zavedený aktualizační příkaz:

```bash
bash ~/update_elektroakademie.sh
```

- Aktualizace musí provést migraci 0020, collectstatic a reload. Pokud nejsou v konkrétní verzi skriptu zahrnuté, proveďte je ručně ve venv před reloadem:

```bash
cd ~/Elektroakademie
source ~/.virtualenvs/elektroakademie-env/bin/activate
python manage.py migrate
python manage.py check
python manage.py collectstatic --noinput
```

- Ověřte stejný průchod novou testovací objednávkou. Staré relace bez oprávnění k objednávce nově nezískávají přístup k náhledu.
- Starší kód nenasazujte přes již používanou fakturační evidenci bez posouzení dopadu; číselnou řadu ani vystavené faktury nemažte kvůli opravě PDF.
